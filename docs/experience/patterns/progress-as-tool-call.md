# Progress checklist sent by the model as a tool call

In two real-phone runs of the same coffee-shop task, the model put the three acceptance goals into the arguments of a tool call named `task_progress`, and only in the next round called the tool to view installed apps. The upstream progress convention puts it in a `<task_progress>` block in the reply body; see commit `13f34294`. The `unknown_tool` in the log and the missing first checklist event point to the difference between these two message formats. A similar progress stall can also happen when the model never creates a checklist, so first look at the raw reply type and the tool name.

`ProgressToolCallTest` replays this shape at the entry of the run loop. It checks whether `RunEvent.Criteria` received the checklist, whether the real action ran once, and whether the next model request returned a result for each call ID in the original order. The misplaced fields still go through the argument and state checks of `CompletionPlanBlock`, and other unknown tools still report an error. For real-phone acceptance, start the same task fresh; past runs keep their original results.

Real-phone joint test review (2026-11-18): among 52 captured replies there were 4 function calls with this name. One submitted the three goals, and the other 3 each confirmed one goal. The run log wrote 4 checklist events in order, with no failure record for this tool and no progress check error, and the final state was `succeeded`. The joint test included the per-goal confirmation feature; when applying the compatibility fix alone, the progress fields are still checked as in that version.
