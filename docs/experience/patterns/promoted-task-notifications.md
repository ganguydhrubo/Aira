# Task notification qualifies but no live capsule shows

On a real Android 16 phone (OnePlus 13T, ColorOS 17), Aira Dev was allowed to post normal notifications, but the system "Live notifications" switch was still off (this maker shows Android 16 live notifications as "Fluid Cloud"). Running `TaskLiveUpdateDeviceTest` with the switch off: the task notification's `hasPromotableCharacteristics()` was true, but `NotificationManager.canPostPromotedNotifications()` was false, and the home screen only showed a normal icon. We opened this app's system page with `Settings.ACTION_APP_NOTIFICATION_PROMOTION_SETTINGS` and `Settings.EXTRA_APP_PACKAGE`, turned it on and ran the same test again: "Working" appeared at the top of the home screen and then changed in place to "Waiting for your answer".

When diagnosing, look at three things separately: whether the notification the app posts meets the [live update conditions](https://developer.android.com/develop/ui/views/notifications/live-update), whether the system allows this app to promote notifications, and whether the system UI really shows it after you leave the app. Looking only at the notification shade, the permission declaration or one system flag cannot replace the last step.

Scope of verification: a Dev update-install on one real Android 16 phone. Do not use it to infer the default switch or menu names on other models, or maker APIs on Android 15 and earlier.

Another case is that the capsule appears but shows only "Working" for a long time. First check the mapping from `TaskState.Running` to the short text. While waiting for the model, `tool` is empty but `note` may still hold the previous step's action; showing `note` directly can report the wrong stage and can also expose task content. `RunProgress.Replay` has the current step and total steps; `RunProgress.Batch` has only the batch length, so do not pair the model round count with that length and call it progress. The older short text used this to tell apart actions, counts and waiting states.

After an update-install of the multi-state version `16e61108` on the same phone, the formal `TaskLiveUpdateDeviceTest` cases passed for both "go to home screen while thinking" and "go to home screen after progress is reported". The home screen showed "Thinking", "Progress 2/5", "Waiting for your answer", and the capsule was removed at the end; all these stages use the same notification. On the first look it once stayed at "Thinking"; the cause was not found, and no system switch was changed because of it. This round did not check, one by one on the phone, the text for screen reading, phone actions and web browsing.

**When the count on the chat page does not move, first tell apart a missed report from a missed refresh.** In one cross-app task, round 1 gave three acceptance criteria and 0/3, and the text in rounds 18 and 23 confirmed two results, but up to round 31 the run log still had only the first `criteria` event, and no `RunEvent.State.name == "task_progress_invalid"`. In this case there was no new structured count for the UI to show. When diagnosing, compare these two kinds of events and the matching `model_reply` within the same run ID; if the log already shows 1/3, then check the UI subscription and priority. `CompletionPlan.apply` keeps fields that were not updated; reporting a piece of text alone, or changing the list of acceptance criteria, does not increase `done` on its own. This is a separate problem from whether the system allows promoted notifications.

**Which stage the task is in** can be judged from the package name the task's tools actually opened, or the page read through the phone port. The stage moves forward by one only in the app order the user gave; unrelated packages, failed opens and going back to the previous app do not change the stage number. This number must not be written into the completed-goals count on the chat page. Different goals inside the same app have no package switch, so they use the stages planned by the AI and its structured report when it starts the next goal. The coffee-shop task in `TaskStagesTest` reproduces the case where three stages still show even though every report was missed; so far this version is verified only on the simulated port, and the system capsule width still needs a recheck on a real phone.

In the real-phone joint test of `558b4a6`, the user could already see Xiaohongshu, but the capsule still showed "1/3 Find address". "Find address" came from the AI plan; when planning by the order the apps were named, the first stage of that original sentence shows "Amap". This 36-step run ended successfully; only a separate 5-step cancelled run had the first-round unknown-tool error. Diagnose by matching screenshots to the run ID. The old regression test ran with an empty app list; after adding test apps named "Search" and "Notes", the same coffee-shop request could not build an order, and the AI stages also ignored the actual app switch; both were reproduced on the JVM. The phone connection dropped, so the actual conflicting app name is not yet confirmed. The regression test `TaskStagesTest` now uses a launcher list and built-in knowledge that contain the same words, and checks that when the AI marks an app for a stage, successfully entering the next app moves the stage forward; two goals inside the same app still need an explicit report. How the system shows the new build still needs a recheck.
