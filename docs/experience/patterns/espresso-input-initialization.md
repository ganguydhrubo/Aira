# Compose device test fails while input is initialising

On their first run, both tests for [personal assistant reply copy #644](https://github.com/ganguydhrubo/Aira/issues/644) failed during `Espresso.onIdle` initialisation with `NoSuchMethodException: android.hardware.input.InputManager.getInstance`. No tap or long press had happened yet, so this result must not be taken as a failure of the copy feature.

When diagnosing, check the Espresso version resolved in the **test APK**. Here, version 3.5.0, pulled in indirectly by the Compose tests, took a reflection path that does not work on an SDK 37 phone; the [Espresso 3.7.0 release notes](https://developer.android.com/jetpack/androidx/releases/test#espresso-3.7.0) list a fix for this. Pin the fixed version only in `androidTestImplementation`, rebuild, update-install the test APK, and run the same test again; there is no need to change the phone's hidden API policy.

Verified once: on the same SDK 37 device and the same Dev app, after replacing only the test package, `PersonalReplyCopyTest` went from two initialisation failures to two passes, including the clipboard assertions for long press, drag select, select all and copy all text.

Where it applies: the stack trace above appears before the test runs. A different failure happens at **clipboard read-back** just after an update-install: the same phone's clipboard (`ClipboardManager`) allows writes but refuses reads because the test window does not yet have focus, so the assertion gets null. After `PersonalReplyCopyTest` waits for `Activity.hasWindowFocus()`, a retest of "update-install → start the test at once" passed. This timing problem is not related to Espresso initialisation; if text is already read but the range is wrong, check the selection in the reply component.
