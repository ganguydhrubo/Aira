# Many actions done, but the goal count never changed

Signal: the task card stays at 0/N, but the action timeline already shows results that can be checked. First compare, for the same run, the `criteria`, the parse-error event (`RunEvent.State.name == "task_progress_invalid"`) and the model replies. Only the first `criteria` and no parse error means no later valid update was received; do not work out completed goals from the number of actions. The collapsed "N earlier steps" on the chat page refers to actions that already happened.

In one cross-app shop-finding task, the replies reported the confirmed address and then the shop name, but the count stayed at the starting 0/3. The old protocol stripped the progress block from the conversation history and did not bring the checklist back in later normal requests. Now `TaskProgressTracker` brings back the IDs still to be confirmed and removes duplicate reports that carry evidence; `RunEvent.Criteria.confirmedIds` can be used to recheck. The counter does not verify the content of the evidence, and does not mark unreported results as done.

Regression entry points: `AgentLoopTest.coffeeTaskConfirmsGoalsWithoutCountingClicksOrClosingOnFiveNotes` checks the to-do the model actually received, 1/3 → 2/3 → 3/3, and that actions can continue when a sub-quantity is reached; `completedQuantityClosesOutInsteadOfRecheckingForever` keeps the close-out behaviour for plain counting tasks. Both are scripted replays and cannot prove that every model reports on time.

Another signal is **no checklist event at all**: when the same coffee-shop task ran again, it ended normally after 30 rounds, but with no checklist and no parse error. The old to-do reminder only looked at a multi-goal checklist that already existed, so it never asked for one to be created late. Now, if the first tool call has no checklist, the next normal request reminds once; the model can report confirmations for results already seen at the same time. Check `RunEvent.State.name == "task_progress_plan_reminder"` to tell apart "a reminder to create the checklist was sent" from "the model actually reported it". If there is still no checklist, keep the action status and do not invent a denominator. The scripted tests `missingChecklistCanBeBackfilledOnTheNextCoffeeTaskReply` and `ignoredChecklistReminderDoesNotRepeatOrInventProgress` verify the late report and the ignored reminder; real model responses still need live testing.

The late-checklist rule is written in the system principles, and at run time only a short marker is sent. Repeating the whole example in the context after tool results triggers compression in the small-window `longTaskStaysUnderBudget` test, which then hides the full screen the model has just read. That test also checks that the first long screen read is kept and that the whole request stays within budget.
